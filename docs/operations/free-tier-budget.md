# 免费额度预算与统计边界

本文用于评估当前统计设计，数字是说明模型的假设，不是生产测量。上线前必须从 Cloudflare 账户指标和 D1 查询 `meta.rows_read`、`meta.rows_written` 验证；本次无法访问账户遥测，因此实际 CPU、读写行数、缓存命中率、隔离区数量和可持续请求量均未知。

## 平台额度

截至 2026 年 11 月，Workers Free 每日 100,000 次请求、每个 HTTP 请求 10 ms CPU、每隔离区 128 MB；请求量包含仪表盘、健康检查及客户端重试。D1 每日 500 万行读取、10 万行写入，账户共享 5 GB 存储。KV 每日 100,000 次读取、1,000 次写入；Analytics Engine 每日包含 100,000 个数据点和 10,000 次查询。以账户实际套餐为准：[Workers 限额](https://developers.cloudflare.com/workers/platform/limits/)、[D1 定价](https://developers.cloudflare.com/d1/platform/pricing/)、[KV 定价](https://developers.cloudflare.com/kv/platform/pricing/)、[Analytics Engine 定价](https://developers.cloudflare.com/analytics/analytics-engine/pricing/)。

D1 索引更新也可能增加计费写入；维护、其他数据库和账户内其他服务共享额度。读取与写入任一日限额耗尽时 D1 查询会失败。预算以账户全部实际写入不超过 70,000 行/日为目标，保留 30% 余量。

## 写入模型

没有近期写入故障时，每个隔离区、每个 D1 绑定的首个 usage 事件会立即触发提交尝试。源码默认刷新间隔为 `60 秒`（`FLUSH_INTERVAL_MS = 60_000`），或累计 `500` 个事件达到阈值时触发；有后续事件时会检查上述条件，聚合读取也可能在节流窗口结束后触发刷新。此外存在隔离区内 `setTimeout` 定时器的尽力而为刷新，但它不属于请求的 `waitUntil()` 承诺，不能保证请求结束或隔离区回收前执行。若 D1 写入失败，事件驱动重试有 60 秒退避。后续待提交数据仍可能随隔离区回收丢失。每个批次、每个小时的 SQL 语句数为 `2 × K + M_delivered + M_upstream`：K 是有数据的 delivered 和未交付 upstream 两种统计类别数；`M_delivered` 是成功交付的不同模型数，`M_upstream` 是未交付尝试中抽中的不同模型数。跨小时的批次需分别计数。成功交付的物理尝试包含在 delivered 行中，失败或取消的物理尝试使用 upstream 行。

| 假设工作负载 | 批次/日 | 每批类别与模型 | 基础 upsert 语句/日 |
| --- | ---: | --- | ---: |
| 单隔离区，稀疏流量 | 至多 10 | 仅 delivered，1 个模型，Token 明细抽样 0% | 至多 30 |
| 5 个隔离区各活跃 8 小时 | 2,400 | 两类均出现，delivered 与抽样 upstream 各 3 个模型 | 24,000 |
| 20 个隔离区全天活跃，高模型基数 | 28,800 | 两类均出现，delivered 与抽样 upstream 各 5 个模型 | 403,200 |

后两行假设流量持续、每个一分钟窗口至少有触发写入的事件、事件数低于每批 500 次阈值；实际隔离区回收、失败退避和尽力而为定时器会改变批次数，事件数达到阈值也可能使批次更频繁。模型数是每批不同的模型数，不是请求数。高模型基数示例已经远超每日 100,000 行的免费写入额度；这仍只是 SQL upsert 语句数，未包含索引、维护与其他数据库写入，不能据此宣称实际账单行数等于该数。默认成本保护将模型 Token 明细抽样设为 1%，全局已观察 usage、模型成功证据与 TTFT 不抽样。首个成功交付的及时写入可减少短生命周期隔离区的数据丢失，但隔离区频繁创建会增加写入，必须结合账户指标评估。SQL 语句数不是 D1 计费行数；首个事件之后的稀疏流量仍可能没有后续事件触发提交。

若两类每批均存在且没有模型行，70,000 条语句对应最多 17,500 个批次；若每批另有 10 个模型行，则为 5,000 个批次。这只是未计索引和其他工作负载的理论上限，不能换算成成功推理次数。成功交付有模型名时至少会写入一个模型行，即使 Token 明细采样率为 0%。上游实际尝试数除以成功交付数才是重试放大率，缓存命中所省的调用和 Token 必须实测。

仪表盘聚合在隔离区内缓存 45 秒，读取不触发待写批次；跨隔离区不共享缓存。统计修复不增加逐请求 KV 写入，也未增加 Analytics Engine 数据点。七天小时行、52 周日/周物化和清理作业仍需计入读取、写入及存储；维护作业的实际行数和索引成本未测量。当前无法计算每 1,000 次物理尝试的实际计费行数，也无法确认 10 ms CPU 或 128 MB 内存余量。

## 额度耗尽时

Worker 无法直接知道账户剩余额度。运营者应检查 Cloudflare 账户指标：使用到 50% 时核对增长趋势；70% 时降低可选模型 Token 明细采样并检查其他消费者；90% 时将该采样降至 0 并减少非必要查询；100% 时 D1 查询失败，推理继续，写失败批次仅在隔离区存活时重试，持久化统计可能滞后或丢失。将采样设为 0 不会停写模型成功证据与 TTFT。仪表盘对读取失败显示不可用；上游未报告 usage 时不估算 Token。上述阈值是人工操作建议，不是自动账户级限流。

Cache API 条目按数据中心隔离，需显式 opt-in 和有效域名；它不保证跨地区命中。单次缓存填充限制 256 KiB。SSE 观察器的行和帧各有 64 KiB 上限，按 16 KiB 输入片段解码；队列、请求体、D1 缓冲、转换和运行时开销另计，实际峰值必须在现有并发限制下测量。[Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) 和 [Workers 限额](https://developers.cloudflare.com/workers/platform/limits/) 描述平台行为。
