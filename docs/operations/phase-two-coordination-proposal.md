# Phase 2 跨 isolate 协调提案

## 状态与范围

本文是供评审的候选设计，不授权实现、配置生产环境或部署。仓库中没有可核实的 T2.1/T2.2 正式任务描述；下列编号只是按现有可靠性边界提出的研究拆分，应在 Phase 2 获得授权后再确认。

T2.1 候选：评估是否需要加强 Tier 1 长冷却的跨 isolate 协调。

T2.2 候选：评估是否需要针对有明确额度证据的请求实施跨 isolate 原子租约。全局并发信号量是另一个更强的变更，不应由本提案默认引入。

## 当前基线

- Tier 1 已用 `TIER1_AFFINITY` KV 尽力共享一小类长冷却：401、账号级长期配额 429，以及持续至少 5 分钟的模型级 403。每个 isolate 首次请求时读取，之后最多每 5 分钟读取一次；KV 最终一致，并发写可能丢失。
- 分钟级 429 保持 isolate 本地，因为同级 key 恢复时可能提前唤醒；跨 isolate 扩散这种状态会导致不必要的冷却。
- `max_in_flight` 是 isolate 本地运营者限制，不代表 Provider 全局容量。额度租约只使用 Provider 明确上报的额度，状态仍为 isolate 本地；每个 hedge 物理派发各自 claim。
- 仓库的免费额度预算没有列出 Durable Objects 的套餐额度或成本，也没有生产隔离区数、操作量和延迟遥测。现在不能推算 DO 的美元成本、免费余量或延迟增量。

详见 [可靠性模型](../architecture/reliability-model.md) 和 [免费额度预算](free-tier-budget.md)。

## 候选方案

### T2.1：长冷却协调研究

先验证现有 KV 的最终一致性是否在真实流量中造成了有害的重复派发。仅当证据显示丢失或并发更新确实导致额外的拒绝请求、429 或明显恢复延迟时，再比较继续使用 KV 与增加 Durable Object 协调的收益。

如果未来批准原型，优先采用状态变化时写入、isolate 初始化或明确触发时读取的模式；避免每次推理请求同步访问 DO。异步更新不会增加正常请求的同步延迟，但也不保证其他 isolate 立即看到冷却。若需要强即时性，必须单独评估热路径读取的成本与延迟。

### T2.2：额度租约研究

先统计同一 Provider 额度窗口上的并发超额、重复 429 及恢复结果。只有在 Provider 明确提供可用于准入的额度数据，且 isolate 本地预留的竞争已造成可量化损害时，才评估原子共享租约。

强制全局 claim 会改变 dispatch 热路径。未知额度仍应保持现有直通语义；不能把推测的 Provider 并发上限转成全局硬拒绝。共享状态出错时采取 fail-open 还是 fail-closed 会直接影响成本与可用性，必须在任何实施前由评审明确决定。当前架构的默认容量信号不足以支持全局信号量。

## 配额、成本与延迟测量

实施前先只读收集同一基线窗口的数据：

- `A/day`：物理 Provider 派发数，包含重试和 hedge。
- `I/day`：新 isolate 的启动或首次 Tier 1 请求次数。
- `U/day`：长冷却状态新增或延长次数。
- `C/day`：同一长冷却在不同 isolate 中引发的重复派发或重复 429 数。
- 成功率、429/401/403、每次成功的物理派发数，以及 TTFT 和端到端延迟的 p50/p95/p99。

这些数据只用于评估，不假设当前已有生产遥测。

候选操作量模型：

- T2.1 若只在 isolate 启动/显式刷新时读取，并在状态变化时写入，日操作量可先按 `I + U` 估算，再另计刷新、冲突处理与重试。该模型不是计费量，也不包括 DO 执行时长和存储。
- T2.2 对每个物理派发至少需要一次 claim，以及一次 settle 或 release；初步模型为 `2 × A` 次协调操作/日，再加实际失败路径产生的重试操作。hedge 的每个物理派发都单独计入 `A`。

上线前必须按目标 Cloudflare 账户和套餐核实 DO 请求数、执行时长、存储、免费额度边界及可能的超额计费；同时确认 Service Binding/内部调用的实际计费归属。不得把其他产品的免费额度套用于 DO。

若做获批的离线原型或 shadow 试验，应在同一区域、相同负载下测量协调往返 p50/p95/p99、超时率、冲突率和拒绝率。T2.1 的异步模式可不增加正常请求的同步 hop，但不能声称即时一致；T2.2 的同步 claim 至少会在每个派发的准入路径增加一次 RPC 往返，且可能因同一对象串行处理而排队。端到端增量须以实测为准。

## 回滚与验收门槛

若后续获准实施：

1. 先保持当前 KV 长冷却、本地 429/额度状态和现有路由行为作为基线；功能开关默认关闭。
2. T2.1 只有在重复派发造成可测损害、且协调成本低于避免的上游失败成本时才进入小范围试点。
3. T2.2 只有在观测到真实额度竞争、并确认 Provider 返回的额度证据足以支持原子结算后才试点；不能以猜测容量设置硬上限。
4. 对照基线比较重复派发、429、成功率、每次成功的物理派发数、TTFT/端到端 p50/p95/p99、协调失败和 Cloudflare 实际用量。具体容忍阈值应基于基线评审后设定，本文不伪造数值。
5. 若成功率下降、延迟超出批准阈值或额度逼近套餐上限，关闭新功能开关并恢复当前 KV/本地行为。DO 状态使用版本化键和有限 TTL；回滚不依赖 Cron，也不要求删除现有 KV 状态。

本提案不包含生产配置修改、Secret/Service Binding 变更、DO 部署、Cron 变更或任何生产 HTTP 请求。这些动作都需另行授权并通过既有发布门禁。
